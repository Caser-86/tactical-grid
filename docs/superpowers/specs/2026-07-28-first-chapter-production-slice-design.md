# 第一章成品垂直切片设计规格

## 目标

将 Tactical Grid 的第一章做成可由普通玩家独立启动、连续游玩并完成的发布候选切片。该切片必须覆盖从新游戏到第一章 Boss 结算的完整流程，并成为第二至第五章复用的内容和质量生产标准。

本规格不宣称完成整个五章游戏。完整成品将在第一章切片达到验收门槛后，按同一管线扩展。

## 当前依据

- 引擎：Godot 4.7.1，主场景为 `res://scenes/boot.tscn`。
- 当前已有：本地存档、基地、任务选择、锁定地图、回合战斗、任务目标、结算、角色成长、商店、对话、Boss 数据、Windows 导出预设。
- 当前自动验证：Godot 无头冒烟测试 985/985 通过；服务端构建与 29 项 Jest 测试通过；30 张锁定地图可加载。
- 当前阻断：没有真实菜单到结算的输入验证；第一章没有完整玩家验收；部分武器/物品效果为空实现；正式美术与音频尚未接入；没有已验收的 Windows 发布包。

## 体验范围

玩家从启动界面开始，创建新存档，进入基地并选择第一章任务。六个任务以渐进方式教授移动、攻击、掩体、交互目标、技能/物品和 Boss 机制。每场胜利都进入结算，奖励、经验、解锁和装备变更保存到本地存档，并影响下一场战斗。完成第一章第六关后，玩家看到章节完成反馈并能返回基地继续保存的进度。

失败路径必须可重试或返回基地，不得破坏已完成进度。暂停、设置、退出、重新启动后继续游戏均必须可用。

## 任务编排

| 关卡 | 主题 | 教学目标 | 胜利条件 | 章节进度效果 |
|---|---|---|---|---|
| `ch1_m1` 初次接触 | 仓库 | 选择、移动、攻击、撤离 | 全部存活单位抵达撤离点 | 解锁 `ch1_m2`，发放首通奖励与经验 |
| `ch1_m2` 掩体战术 | 仓库 | 掩体、高地、破坏目标 | 摧毁指定目标 | 解锁 `ch1_m3`，验证基地成长闭环 |
| `ch1_m3` 高地优势 | 仓库 | 警戒和射程 | 撤离 | 解锁 `ch1_m4` |
| `ch1_m4` 护送协议 | 仓库 | 交互与护送 | VIP 到达撤离点 | 解锁 `ch1_m5` |
| `ch1_m5` 破局 | 仓库 | 技能和物品 | 关卡目标完成 | 解锁 `ch1_m6` |
| `ch1_m6` 数据哨兵 | 仓库 Boss | Boss 预警、阶段和应对 | 击败 Boss | 第一章完成、章节成就与过场反馈 |

每关必须在 `levels.json`、锁定地图、战斗目标、对话和结算奖励之间具有一致的关卡 ID、任务类型、单位数量和胜利条件。

## 架构与数据流

### 场景流程

`Boot` 负责初始化并进入 `MainMenu`。`MainMenu` 创建或恢复本地存档后进入 `Base`。`BaseController` 使用 `CampaignRepository` 和 `GameManager.current_save.campaign_progress` 显示可选任务。选择任务后，`GameManager.go_to_battle(level_id)` 设置当前关卡并加载 `Battle`。

`BattleController` 只从客户端锁定地图读取关卡地形和目标，创建单一战斗状态源，完成后调用 `GameManager.complete_mission(result)` 或 `GameManager.fail_mission(result)`。结算场景只展示 `GameManager.battle_result`，并提供重试、返回基地和下一关操作。

### 存档与成长

`GameManager.complete_mission(result)` 是唯一的胜利持久化入口。它记录完成关卡、评分、下一关、基础奖励、一次性首通奖励、经验和成就。`SaveManager` 使用本地原子写入与备份恢复，所有基地操作（购买、装备、分配属性、学习技能、设置更改）立即保存。

第一章的每个配置奖励必须是实际可消费的货币、经验或可识别的库存物品。任何配置中的战利品 ID 必须在 `GameData` 的武器或物品目录中存在；无效战利品必须在构建期测试失败，不能写入不可显示的库存。

### 教程与提示

教程由 `levels.json.tutorial_flags` 驱动。每个教学点必须只在首次需要时展示，可跳过，并在设置或暂停菜单中重看。提示说明真实输入、目标和失败恢复，不得以仅显示文本替代未实现机制。

### 战斗规则补全

第一章可使用的武器、技能和物品都必须有可观察结果。优先实现现有空分支：消音判定、陷阱放置与触发、投掷物范围效果、武器 `special` 效果。未实现的配置项不得向玩家显示为可用操作。

Boss 必须至少拥有可读的阶段切换、一次预警、专属能力和失败/胜利反馈。Boss 阶段数据必须由现有 Boss 数据文件驱动，并有自动测试验证阶段阈值。

## 表现与资源策略

第一章先接入一套完整、可商用且可追溯的最小资源包：64x64 地形、玩家与敌人战斗单位、目标物、统一 UI、枪击/命中/爆炸/治疗/升级反馈、菜单和战斗音效。

资源只能来自项目已有可合法使用资源、可商用且允许修改的开源资源、程序化生成或 AI 生成。每个新资源必须记录来源、许可证或生成信息、修改说明和游戏内路径。已有带水印图片不得进入发布包。

正式批量资源之前，先在 `ch1_m1` 与 `ch1_m6` 验证尺寸、透明通道、导入设置、动画锚点、碰撞、可读性与性能。小样失败时仅调整小样，不扩散至全部关卡。

## 验收与测试

### 自动验证

- 保持 Godot 无头冒烟测试全绿，并为每项新增规则补回归。
- 新增场景流程测试：新游戏、选择 `ch1_m1`、结束战斗、结算、返回基地、选择 `ch1_m2`、保存、重启、继续。
- 关卡数据测试：六关的任务类型、目标、地图对象、对话、奖励和 Boss 数据一致。
- 成长测试：奖励、升级、购买、装备、第二关单位属性与重启持久化正确。
- 资源测试：所有已引用纹理、音频和场景资源存在；任何资源都具备资源清单条目。
- 发布测试：导出的 Windows 包在无 Godot、无 Node 的目录启动并可创建新存档。

### 人工验收

- 以鼠标和键盘从新游戏连续完成第一章，至少一次失败并重试。
- 在 720p、1080p、1440p 和常见宽屏下检查布局、焦点导航、可读性和暂停/设置操作。
- 记录每关体验、软锁、错误、难度异常、资源缺失与音频缺失；未关闭的 P0/P1 问题阻断发布。

## 完成定义

第一章发布候选满足以下条件时才标记完成：

1. 玩家无需 Godot 编辑器或 Node 服务即可启动 Windows 包。
2. 新存档可连续完成六关并进入第一章完成反馈。
3. 主菜单、基地、战斗、结算、暂停、设置、失败、重试、胜利、存档与继续全部可用。
4. 所有第一章可见技能、物品、目标和 Boss 能力均实际生效。
5. 所有已接入美术和音频资源可追溯且无水印、无缺失引用。
6. 自动测试、人工流程检查和发布包检查均无未解释错误。

## 明确不在本切片中完成

- 第二至第五章的人工关卡策展、剧情和 Boss 成品化。
- 新游戏+、Roguelike、每日挑战及非第一章扩展模式的内容完善。
- 全战役最终平衡和所有结局的发布验收。

这些项目将在第一章验收后，以相同的质量门逐章执行。
