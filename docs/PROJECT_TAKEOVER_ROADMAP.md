### 0.3 已实现且可保留

- Boot、主菜单、基地、设置、暂停、错误提示、加载、对话、结算、角色和商店场景已经建立。
- 离线优先流程、本地存档、备份恢复、损坏恢复、迁移、剧情旗标、结局和新游戏+已有实现和测试。
- 战斗已经具备单位生成、分层渲染、选择、移动、攻击、回合状态机、AI、胜负转场、结算和遥测基础。
- 网格、寻路、视线、战斗公式、状态效果、成长、装备和部分经济逻辑已有自动测试。
- TypeScript 地图生成器已显著提高稳定性，并生成 30 张版本锁定地图。
- Windows x64 导出预设已经创建。

### 0.4 仍然阻止成品闭环的事实

1. 30 张锁定地图只存在于 `server/data/generated_maps/`；Godot 客户端没有引用这些文件。真实战斗仍由 `battle_controller.gd` 使用另一套简单随机逻辑现场生成地图，因此“正式种子通过”尚未转化为玩家可玩的正式关卡。
2. 任务类型没有形成统一目标状态机。`steal_data` 没有终端交互，`escort` 没有护送单位，`defend` 和 `infiltrate` 退化为歼灭，`assassinate` 没有指定 Boss/目标单位。
3. `destroy` 任务没有可破坏目标实体；当前计数只会在敌人恰好死于目标坐标时增加，不能作为可交付任务机制。
4. HUD 的技能按钮固定调用 `gen_overwatch`，物品按钮固定调用 `med_kit`，没有根据角色配置或玩家选择执行真实技能/物品。
5. 武器消音器、陷阱、武器特殊效果、投掷范围效果和增援生成仍有 TODO 或空实现。
6. 189 项测试证明了许多逻辑函数，但不等于玩家从菜单开始、选择任务、操作战斗、结算、继续下一关的真实输入流程已经通过。
7. Godot 战斗与测试退出仍报告 RID、ObjectDB 和资源泄漏；发布候选版本不能带着这些错误通过验收。
8. 当前 UI 和战场是工程表现，没有正式地形、角色动画、特效、图标和视觉层级。
9. 项目内没有任何实际音频；`AudioManager` 只拼接尚不存在的 `res://assets/audio/` 路径。
10. 现有 16 张图片没有被场景或脚本引用，且此前检查到水印、无透明通道和拼贴问题，只能作为内部参考。
11. 项目内没有 LICENSE、第三方通知、AI 资源生成记录或归属清单。
12. Windows 导出预设存在，但没有实际发布构建和干净环境测试；应用图标、文件版本、产品版本和版权字段仍为空。

## 4. 已确认的阻断和缺口

### 4.1 P0：项目无法启动

1. `main_menu.tscn`、`base.tscn` 和 `battle.tscn` 使用无效的 `[attached_script]` 标签。Godot 报 `Unknown tag 'attached_script'`。
2. `enemy_templates.gd:212` 和 `utility_ai.gd:128` 缩进/参数分隔错误，脚本无法解析。
3. `action_system.gd` 使用未声明的 `target_data`，并从声明为 `Dictionary` 的函数返回 `null`。
4. `battle_controller.gd` 从声明为 `Dictionary` 的函数返回 `Unit/null`。
5. `unit_sprite.gd` 使用不存在的 `Color.opacity05` 和 `Color.opacity06`。
6. `api_client.gd` 自定义 `_get(path: String)`，与 Godot `Object._get(StringName) -> Variant` 冲突。
7. `GameManager` 是 Autoload，依赖上述坏脚本后无法实例化；其他 Autoload 和 UI 脚本随之连锁编译失败。
8. `start.bat` 指向不存在的 `..\Godot_v4.6.3-stable_win64.exe`，并且只打开编辑器，要求玩家手动按 F5。

### 4.2 P0：前后端契约不一致

1. Godot 客户端写死 `http://localhost:3001/api`，服务端默认监听 `3000`。
2. 当前玩家必须另行启动 Node 服务，无法作为独立单机游戏发布。
3. `/api/saves/latest` 位于 `/api/saves/:save_id` 之后，实测请求被动态路由截获。
4. 战役列表在服务端硬编码，未读取 `levels.json`，也未根据玩家存档计算解锁状态。
5. 服务端 `data/` 中大部分 JSON 没有被服务端源码读取。
6. 基地选择任意关卡后，战斗场景仍固定请求 `ch1_m1`，所选关卡会丢失。
7. 基地先发起异步 `GameManager.load_level()`，随后立即切换场景；战斗场景又重复请求地图，存在竞态和重复生成。

### 4.3 P1：场景和 UI 只有骨架

1. 项目只有 4 个 `.tscn`，其中设置、暂停、结算、角色、商店、对话、教程均无对应场景。
2. `base_controller.gd` 使用 `$Center/MissionList`，实际节点是 `$Center/ScrollContainer/MissionList`。
3. 基地底部 4 个按钮没有连接任何行为。
4. `battle.tscn` 的 HUD 脚本没有合法挂载，结束回合按钮也没有信号连接。
5. `hud.gd` 构造了单位信息字符串，却没有写入 Label。
6. `main_menu.gd` 的继续按钮永远禁用，设置按钮为空实现。
7. 结算脚本没有场景，也没有被胜负流程调用。
8. 没有暂停菜单、确认退出、错误提示、加载界面、键盘/手柄操作或输入映射。
9. 没有统一 UI 主题、字体资源、焦点导航、分辨率/全屏选项。

### 4.4 P1：战斗循环未闭合

1. `BattleController` 和 `GameManager` 都生成单位，形成两个状态源。
2. `GameData.create_player_unit()` 声明返回 `Dictionary`，实际返回 `Unit` 节点。
3. 战斗显示的是 `UnitSprite`，`Unit` 本身没有加入场景树，导致 `_ready()`、分组和回合刷新不可靠。
4. 移动通过 `spend_ap(0)`，没有实际行动成本。
5. `_clear_overlay()` 只执行 `pass`，高亮会持续堆积。
6. 地图和移动高亮共用同一个 `Overlay` 容器，无法可靠清理。
7. 玩家攻击、技能、物品、警戒按钮没有接入 `ActionSystem`。
8. `_get_skill_data()` 固定返回空字典，因此所有技能入口都会失败。
9. 68 个技能中只有 21 个有分发分支，且其中多个仍是空效果或不完整效果。
10. `use_item()` 引用不存在的 `target_data`，投掷物流程不可用。
11. 移动点被永久扣减，回合开始没有恢复基础移动点。
12. 敌方移动不占 AP，若 Utility AI 连续选择移动，存在循环或不合理多次移动风险。
13. 敌人增援只打印日志，不会生成单位。
14. 胜利检查只处理“玩家全灭”，胜利条件主体是 TODO，因此正常任务无法获胜。
15. 回合上限到达后只执行 `pass`，不会失败或结算。
16. 没有交互目标、撤离判定、护送、守点、暗杀、Boss 阶段和可破坏物的完整逻辑。
17. 没有镜头控制、动画锁、行动队列、反馈时序或输入状态机。

### 4.5 P1：AI 和战术规则不完整

1. Utility AI 和敌人模板目前无法编译。
2. 20 种普通敌人只有约 7 种显式行为模板，其余使用默认模板。
3. 5 个 Boss 数据没有被 `GameData` 加载，也没有 Boss 控制器。

## 5. 首发版本的产品与技术边界

为了把项目真正做完，首发版本采用以下明确边界：

### 5.1 首发目标

- 平台：Windows x64。
- 引擎：固定 Godot `4.7.1.stable`，使用已安装的同版本导出模板。
- 类型：单人、离线优先、俯视角 2D 回合制战术战棋。
- 玩家流程：启动 -> 主菜单 -> 新游戏/继续 -> 教学 -> 基地整备 -> 任务 -> 结算 -> 解锁/成长 -> 最终 Boss -> 结局 -> 通关后状态。
- 战役目标：保留 5 章、30 个主线任务和 5 个 Boss 的数据框架；每关必须有可验证目标、敌人编成、奖励和完成条件。
- 正式内容门槛：主线从头到尾可通关；10 个支线和 Roguelike 只有在主线质量门通过后才进入首发候选。
- 输入：鼠标键盘完整可玩，保留手柄扩展接口。
- 语言：首发简体中文；所有文本从代码中抽离，为后续本地化留接口。

### 5.2 明确不作为首发阻塞项

- PvP、赛季、公会、社交、创意工坊、MOD、载具和移动端发布。
- 云存档、账号系统和在线遥测。
- 这些内容保留设计文档，不删除，但必须在单机正式版完成后重新立项。

### 5.3 架构决策

1. **离线运行优先**
   Godot 客户端不再依赖本地 Node 服务才能开始游戏。认证、战役读取、任务开始、存档和结算全部必须离线可用。

2. **保留 Node 地图生成器，但改为构建期工具**
   修复生成器后，用它批量生成并锁定 30 个主线地图 JSON；正式游戏加载随包地图。随机挑战可在后续通过 Godot 端生成器或预生成池实现。

3. **客户端 JSON 为首发内容单一来源**
   关卡、职业、敌人、技能、物品、奖励和对话统一由 Godot `GameData` 读取和校验。服务端若保留，只消费同一份构建产物。

4. **一个战斗状态源**
   `GameManager` 管全局流程，`BattleController` 管单场表现，`BattleState`/战斗模型拥有单位和目标状态。禁止 `GameManager` 与场景分别生成两套单位。

5. **数据模型与视图分离**
   `Unit` 负责战斗数据和行为，`UnitView` 负责 Sprite、动画和反馈；二者通过信号通信。单位模型必须进入场景树或由明确的纯数据模型替代，不能处于当前半节点半字典状态。

6. **场景按玩家流程组织**
   建立 Boot、MainMenu、Base、Battle、MissionResult、Settings、Pause、Dialogue 和 Ending 场景；可复用面板做独立子场景。

7. **版本化、原子化本地存档**
   存档采用临时文件写入后替换、自动备份、版本迁移和损坏回退。网络同步不影响本地游戏。

## 7. 测试策略与统一质量门

### 7.1 自动测试层级

1. TypeScript 单元测试：随机数、生成器、校验器、服务端可选 API。
2. Godot 核心测试：网格、寻路、视线、战斗公式、状态、目标和存档迁移。
3. Godot 场景测试：Boot、菜单、基地、战斗、结算、设置。
4. 自动对局：检测 AI 卡死、回合上限、目标可完成性和数值异常。
5. 发布包冒烟：在导出后的 `.exe` 上验证，不以编辑器运行代替。

### 7.2 每个任务的完成定义

任务只有同时满足以下条件才能勾选：

- 有明确复现或失败测试。
- 实现已经接入真实场景/流程。
- 相关自动测试通过。
- Godot 无头导入和启动回归通过。
- 没有新增未解释的错误或警告。
- 玩家可见功能经过实际操作验证。
- 资源有来源和许可证记录。
- 路线图中的状态、验证证据和已知限制已更新。

### 7.3 禁止的“完成”判定

- 只有脚本文件，没有场景实例。
- 只有按钮，没有信号和状态变化。
- 只有 JSON 条目，没有游戏内行为。
- 只有生成图片，没有切图、透明、动画、碰撞和导入验证。
- 只有音频管理器，没有实际音频和触发。
- 只在 Godot 编辑器能运行，导出包未验证。
- 只跑后端测试，就声称游戏通过测试。

## 8. 资源与许可证流程

每个资源必须在清单中记录：

| 字段 | 要求 |
|---|---|
| 文件路径 | 游戏内最终文件 |
| 类型 | AI 生成、程序化、自有、开源 |
| 来源 | 工具/仓库/作者和原始链接 |
| 许可证 | 许可证名称、版本和条款链接/快照 |
| 生成信息 | 模型、日期、提示词或生成脚本版本 |
| 修改记录 | 裁切、去背、切片、调色、动画等 |
| 用途 | 场景、角色、UI 或音频触发 |
| 验证 | 无水印、Alpha、尺寸、导入和游戏内截图 |

处理规则：

- 来源不明的资源不进入仓库。
- 不从商业游戏提取资源。
- 不把“网上可下载”视为授权。
- AI 资源必须确认所用服务条款允许目标用途。
- 开源资源必须核对具体版本和许可证，不只记录网站名称。
- CC-BY 等需要署名的资源必须进入游戏 Credits 和第三方通知。
- 现有 16 张带水印图片暂时标记为 `reference_only`，正式批量制作时替换。

## 10. 风险与控制

| 风险 | 当前证据 | 控制方式 |
|---|---|---|
| 设计范围失控 | 文档包含 PvP、赛季、公会、MOD 等大量系统 | 首发只做单机主线闭环，扩展系统另行立项 |
| 前后端耦合阻止发布 | 客户端依赖 localhost API | 离线优先，Node 改为构建期工具 |
| “有数据等于有内容” | 30 关、68 技能多数未接入 | 每条内容必须有行为测试和游戏内验收 |
| 生成地图不可完成 | 压测仅 84.7%，正式种子 6 个失败 | 正式种子 100% 门禁、人工策展、锁定产物 |
| 美术无法商用或不可切片 | 全部图片带水印且无 Alpha | 小样先行、来源清单、重新生成/程序化制作 |

## 11. 本轮未确认事项

## 12. 路线图维护规则

- 本文件是后续执行的主任务表。
- 每次开始任务时记录任务 ID，不在路线图外悄悄扩展范围。
- 每次完成任务时补充实际测试命令和结果，再勾选。
- 新发现的问题按 P0/P1/P2/P3 分级插入对应阶段。
- 若任务改变核心游戏类型、删除大量有效内容、引入付费服务或存在许可证风险，暂停并请求项目所有者确认。
- 其余实现、结构、数值和 UI 细节由项目负责人按本路线图自主决策。
